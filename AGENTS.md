# Agent Instructions

Guidance for AI coding agents working with the opinionated-mixins repository.

## Project Overview

This project provides reusable mixin classes for common model patterns across
Python storage frameworks (ORMs and ODMs). It ships consensus-based defaults:
field names, enum values, and behaviors are chosen by researching conventions
used by popular platforms and frameworks. Proposals require at least three
independent real-world references, weighed by the consensus criteria in
`docs/rfcs/README.md`.

## Build & Development

## Architecture

### Source Layout

```text
src/opinionated_mixins/
├── __init__.py
├── __about__.py         # Compatibility import for the VCS-derived version
├── _version.py          # Generated by hatch-vcs; do not edit
├── enums.py             # Shared enums
└── contrib/             # Framework-specific implementations
    ├── sqlalchemy/
    ├── sqlmodel/        # Re-exports SQLAlchemy implementations
    ├── mongoengine/
    └── odmantic/
```

Do not create new top-level subpackages under `src/opinionated_mixins/`.
New mixins belong in their framework adapter; shared enums belong in `enums.py`.
The package layering is enforced by import-linter (`[tool.importlinter]` in
`pyproject.toml`): `sqlmodel` may re-export `sqlalchemy` mixins, while
MongoEngine and ODMantic remain independent. Add a new framework adapter only
with an architecture update to that contract.

### Mixin Design

A mixin is a plain class composed with a framework base by consumers. Never
inherit from a framework base in the mixin itself; mixins must remain composable
and are not independently instantiated.

Each framework adapter implements the same mixins with consistent field names
and behavior, expressed using that framework's idioms. SQLModel re-exports the
SQLAlchemy implementations rather than duplicating them. Shared enums live in
`src/opinionated_mixins/enums.py`.

Keep the base package free of runtime dependencies; frameworks are development
or optional dependencies. Use framework-native field declarations while
maintaining the same public behavior across adapters.

### Adding Mixins or Fields

1. Read existing RFCs for similar work and write an RFC first
   (`docs/rfcs/TEMPLATE.md`). Implementation begins after acceptance.
2. Research at least three independent real-world references for field-naming
   or enum-value decisions, resolve conflicts with the consensus criteria in
   `docs/rfcs/README.md`, and document the rationale in the RFC.
3. Add shared enums to `src/opinionated_mixins/enums.py`.
4. Implement in applicable framework adapters with consistent field names.
5. Give each mixin its own file per framework and re-export it from that
   framework's `__init__.py`.
6. For SQLModel, re-export the SQLAlchemy implementation.
7. Mirror the contrib structure in tests under `tests/<framework>/`.

The issue templates for model, field, and framework proposals are optional
intake for an RFC; see `docs/rfcs/README.md`.

RFCs in `docs/rfcs/` preserve the design rationale offline. The index at
`docs/rfcs/INDEX.md` is generated and must not be hand-edited; see
`docs/rfcs/README.md` for the process. When asked why a field or mixin works a
certain way, read its RFC before answering.

## Key Conventions

- Source lives in `src/opinionated_mixins/`; tests mirror it under `tests/`.
- `src/opinionated_mixins/_version.py` is generated by hatch-vcs; never edit it.
- Use absolute imports and strict typing; Ruff enforces a maximum cyclomatic
  complexity of 5.
- Versions come from Git tags; do not hand-edit a version literal.
- Commit messages follow Conventional Commits; releases are automated by
  release-please.

## Pull Requests

CI enforces these conventions:

- Branch names follow Conventional Branch:
  `<type>/<short-description>` (for example, `feat/add-login`). Allowed types
  include `feature`/`feat`, `bugfix`/`fix`, `hotfix`, `release`, `chore`, and
  the AI-agent prefixes `ai`, `copilot`, `cursor`, `claude`, and `codex`.
  Descriptions use lowercase alphanumerics separated by single `-` or `.`.
  Automation branches such as `renovate/*` and `release-please--*` are
  whitelisted and should be left as-is.
- PR titles follow Conventional Commits (for example, `feat: add login`). The
  title becomes the squash commit parsed by release-please.
- Human-authored PRs must link an issue with a `Closes #N` keyword unless the
  PR carries the `no-issue` label. Bot-authored PRs are skipped automatically.
