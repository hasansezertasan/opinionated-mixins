# RFC Process Design

**Date**: 2026-04-24
**Author**: hasansezertasan
**Issue**: [#47](https://github.com/hasansezertasan/opinionated-mixins/issues/47)
**Status**: Approved (pending implementation)

## Problem Statement

Proposal context is currently fragmented across GitHub issues, PRs, and code:

- GitHub issue/PR comments can be deleted, losing rationale forever
- AI agents working offline cannot access GitHub-hosted discussions
- Reference implementations from proposals are not preserved after merge
- "Why was field X named Y?" requires opening GitHub
- Repository has implementation but lacks spec/reference documentation
- New contributors may repeat already-rejected proposals

## Solution Overview

Adopt an in-repo RFC (Request for Comments) process. Every new mixin, field
addition, framework adoption, and breaking change is documented as a markdown
file in `docs/rfcs/`. The merged RFC is the canonical, offline-readable spec
— readable on a subway, by an AI agent without GitHub access, or by a future
contributor years later.

ADRs (Architecture Decision Records) are deferred. RFCs include an
"Implementation Notes" section that absorbs implementation-time decisions.
A separate `docs/decisions/` directory may be added later if orphan decisions
(unrelated to any RFC) accumulate.

## Decisions

| Topic | Decision | Rationale |
|-------|----------|-----------|
| Format | RFC + "Implementation Notes" section (no separate ADRs) | Most decisions tie to a mixin proposal; orphan ADRs would be rare in this project |
| Issue templates | Keep existing (model/field/framework proposal), add RFC reference | They serve as low-friction intake; existing research tables are reusable |
| Numbering | Sequential, zero-padded (`0001-slug.md`) | Stable references ("RFC-0005"); date already in frontmatter |
| Scope | Mixin-related only | Project's "research first" philosophy applies to mixins; tooling/CI rarely needs spec-level rationale |
| Backfill | Full — every existing mixin | Consistency; avoids ambiguous "was it skipped or unwritten?" |
| Process docs location | `docs/rfcs/README.md` | Co-located with RFCs themselves, self-contained |
| Status enforcement | GitHub Action auto-updates frontmatter from PR labels on merge | No manual sync, no drift |
| INDEX.md | Auto-generated by GitHub Action | Pure derived data |
| Number assignment | Author picks at PR open | Simplest; collisions practically impossible with sole contributor |
| Template structure | Unified template + `type:` frontmatter field | Single template, machine-validatable |

## Workflow

### Two valid paths

**Path A: Direct RFC PR**
```
RFC PR (with rfc + status:* labels)
  → merge
  → workflow updates frontmatter + INDEX.md
  → implementation PR(s) reference RFC
```

**Path B: Issue-first**
```
Issue (model/field/framework proposal template)
  → discussion
  → RFC PR referencing issue (Discussion Summary section distills issue comments)
  → merge
  → workflow updates frontmatter + INDEX.md
  → implementation PR(s) reference RFC
```

The issue step is optional. Sole contributors or experienced authors can use
Path A directly.

### Status lifecycle

```
draft → proposed → accepted    (PR merged with status:accepted)
                 → rejected    (PR merged with status:rejected, or closed)
                 → deferred    (PR merged with status:deferred)
                 → withdrawn   (PR merged with status:withdrawn)

accepted → superseded          (when newer RFC's `supersedes:` points here)
```

Maintainer discretion: rejected/deferred/withdrawn RFCs **may** be merged for
the record. Not mandatory — judgment per RFC. Merging preserves rationale
offline; closing reduces clutter.

## Directory Layout

```
docs/
└── rfcs/
    ├── README.md          # Process documentation
    ├── TEMPLATE.md        # RFC template
    ├── INDEX.md           # Auto-generated
    ├── 0001-created-at-mixin.md
    ├── 0002-updated-at-mixin.md
    └── ...
```

Flat directory. No status subdirectories — frontmatter is the source of
truth, INDEX.md groups by status for browsing.

## RFC Frontmatter Schema

```yaml
---
rfc: "0005"                    # 4-digit zero-padded string
title: TaggableMixin
type: mixin                     # mixin | field | framework | breaking-change
status: draft                   # draft | proposed | accepted | rejected | deferred | withdrawn | superseded
created: 2026-04-24             # ISO date when RFC PR opened
updated: 2026-04-24             # ISO date last status change
author: hasansezertasan
github_issue: 47                # null if direct path
github_pr: 52                   # auto-filled by workflow
supersedes: null                # RFC number this replaces, or null
superseded_by: null             # RFC number that replaces this, or null
---
```

## RFC Template Body

```markdown
# RFC-XXXX: <Title>

## Summary
One paragraph. What is being proposed?

## Motivation
Why does this matter? What problem does it solve?

## Research
Industry consensus check. Minimum 3 references for naming/enum decisions.

### Field Naming (mixin/field RFCs)
| Source | Field Names Used | Link |

### Enum Values (if RFC introduces enum)
| Source | Field | Values |

### Framework Adoption (framework RFCs only)
| Metric | Value | Link |

## Design

### Fields (mixin/field RFCs)
| Field | Python Type | Required | Default | Constraints |

### Enum Additions (if any)
Code block with proposed enum.

### Reference Implementation
Per-framework code blocks (SQLAlchemy, MongoEngine, ODMantic).

### Framework Mixin Idioms (framework RFCs only)
How does the framework express mixins?

## Alternatives Considered
Each alternative with rejection reason.

## Discussion Summary
Distilled from originating issue if applicable.

## Consequences
What becomes possible? New constraints? Migration required?

## Implementation Notes
(Filled post-merge.) Deviations from RFC during build.

## References
Links to issue, PR, external docs.
```

## INDEX.md Format

Auto-generated. Sections in order:

1. **Active RFCs** — `accepted` and `proposed` statuses
2. **Rejected / Deferred / Withdrawn** — with reason column
3. **Superseded** — with link to replacement RFC
4. **By Type** — quick filter footer

Auto-generation triggers: PR merge with `rfc` label.

## GitHub Action Workflow

`.github/workflows/rfc.yml`

**Trigger**: PR merged to `main` with `rfc` label and changes to `docs/rfcs/*.md`

**Steps**:
1. Read PR labels, find `status:*` label
2. Fail if no `status:*` label (also enforced via branch protection)
3. Update frontmatter `status:` and `updated:` fields in modified RFC files
4. Set `github_pr:` field if not already set (first merge of the RFC file)
5. Regenerate INDEX.md from all RFC frontmatters
6. Commit back to main with `chore(rfc): sync status from PR labels [skip ci]`

**Required PR labels**:
- `rfc` (marks PR as RFC)
- One of: `status:accepted`, `status:rejected`, `status:deferred`, `status:withdrawn`

**Branch protection** (manual GitHub config):
- Require `rfc` label + one `status:*` label before merge
- Require workflow check to pass

`status:superseded` is auto-derived (not a PR label) — workflow detects when
another RFC's `supersedes:` field points to an RFC, sets that RFC's status
to `superseded`.

## Backfill

**Granularity rule**: one mixin per RFC, even if originally introduced in a
batch PR. Each mixin has independent rationale and may evolve separately.

**Mixins to backfill** (existing implementations):

| 0007 | ActivityMixin | #42, #45 |

(Final list confirmed by reading source during execution.)

**Process per mixin**:

1. Read existing implementation across all contrib modules
2. Read original PR description and any linked issue
3. Fill RFC template:
   - `created` = original PR merge date
   - `status` = `accepted`
   - `github_pr` = original PR number
   - **Research** — reconstruct from original proposal issue (or note "backfilled — research preserved from issue #N")
   - **Reference Implementation** — current implementation (it is what was decided)
   - **Discussion Summary** — distill from original PR/issue comments while still accessible
4. Single PR for all backfills, labeled `rfc` + `status:accepted`

## Execution Order

1. Bootstrap infrastructure: TEMPLATE.md, README.md, INDEX.md skeleton, workflow
2. Update CONTRIBUTING.md, CLAUDE.md, issue templates
3. Backfill PR (all retroactive RFCs in one PR)
4. First "real" RFC uses the new process end-to-end (validates flow)

## Success Criteria

- All existing mixins have RFCs (offline-readable rationale)
- Future mixin proposals must produce RFC before implementation
- Status frontmatter never drifts from PR labels (workflow enforced)
- INDEX.md always reflects current state (auto-generated)
- AI agents working offline can answer "why field X named Y?" by reading the RFC
- New contributors discover RFC process via CONTRIBUTING.md and issue templates
- Comment deletion on GitHub does not lose proposal context (it lives in the merged RFC)

## Out of Scope

- Separate ADR system (`docs/decisions/`) — deferred until orphan ADRs accumulate
- RFC review/approval automation beyond label sync (e.g., required reviewers per type)
- Automatic research validation (counting references, checking links work)
- Cross-RFC dependency tracking beyond `supersedes`/`superseded_by`
